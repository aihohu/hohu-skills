# ADR 0001：共享工作流与项目级安装

状态：已采用。

## 背景

HoHu 业务开发涉及后端、Web、CLI 和应用 AI 工具。不同编程助手需要不同发现目录，但框架规则和开发流程应保持一致；框架包版本也可能对应不同源码契约。

## 决策

1. **单一工作流、独立安装适配** — 在 `skills/` 维护唯一内容，安装器只调整目录位置。**反例**: 分别维护 Codex 和 Claude 开发清单，导致权限要求漂移。**回归**: [辅助脚本测试](../../tests/test_helpers.py)检查宿主安装内容一致。
2. **结合版本、提交和能力检查** — 包版本不足以标识确认网关契约，未知源码需要审查。**反例**: 将所有 0.1.5 源码直接视为兼容。**回归**: 辅助脚本测试覆盖未知源码及能力缺失。
3. **限定项目发现范围** — 仅识别明确的组件和项目边界。**反例**: 空验收目录误选外层正在使用的应用。**回归**: `test_no_guessing_unrelated_root`。
4. **编码授权与业务确认分开** — 生成的写入工具仍遵守应用权限和 Gateway 确认。**反例**: 因用户授权开发而绕过实际用户确认。**回归**: [独立项目验收](../validation.md)检查预演、拒绝、批准、重放及权限撤销。
5. **引用框架教程，不复制实现** — 框架契约和完整教程各有维护来源，Skill 负责组织执行。**反例**: 将完整 Notes 脚手架复制到 Skills 后独立演进。**回归**: 审查 Skill 引用及所支持源码，按独立项目验收检查接线。
6. **按职责拆分两个 Skill** — 项目生命周期使用 CLI，业务模块遵守目标规范并默认接入 AI；国际化按用户要求或目标惯例，不引入能力配置体系。**反例**: 创建项目时要求填写业务能力开关，或复制教程平铺结构作为新模块标准。**回归**: 两个 Skill 安装测试、CLI 创建回归以及单语言/既有模块场景审查。

## 影响

在线安装交由通用 skills CLI，HoHu CLI 固定安装器版本并包装同一入口；两者共用上游管理记录。上游可能覆盖现有内容，更新前审查并备份定制。本地 Python 复制备用工具仍要求显式目标项目，遇到不同内容会拒绝覆盖。检查器不会自动升级框架，结构检查通过仍需要实际业务验证。

租户归属清单、迁移回归、实际路由生成方式和工具标题翻译都属于模块集成要求，具体执行位置由 Skill 参考资料维护，不在 ADR 复制任务清单。
